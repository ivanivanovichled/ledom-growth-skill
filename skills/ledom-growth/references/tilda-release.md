# Tilda: чтение, правка и выпуск

## Инструменты и выбранная страница

В каждом чате заново проверить официальный Tilda MCP и схему точной операции. Если функция поддерживается — использовать MCP. Не заменять чтение/редактирование браузером из-за неудобства или отсутствия браузерной авторизации. Перед изменением подтвердить проект, домен, pageid, URL и нужные блоки по свежим ответам.

Ориентиры инструментов, не замена текущей схеме:
- списки проектов/страниц, настройки страницы и блоки — найти текущие get/list-инструменты;
- `edit_record` читает поля вкладки, а не сохраняет их; `update_record` сохраняет; проверить полную схему и предписанный цикл чтения;
- `update_page_settings`, блоки, head/CSS, redirects, robots/sitemap могут иметь обязательные поля или полную замену; прочитать исходное значение и сохранить всё незатронутое;
- перед Vibe прочитать `vibe_block_generation_instructions`, design/forms-инструкции по необходимости;
- публикация и сохранение — разные операции. Найти точный publish-инструмент и проверить его результат.

Предпочитать Vibe Block для новых статей/посадочных, Zero Block — по прямому выбору владельца или конкретной необходимости. При отсутствии MCP проверить конфигурацию только по названиям серверов, не выводить ключи. Указать точную неподдерживаемую/недоступную функцию и выбрать безопасный fallback. Ошибка одной функции не отменяет другие доступные операции.

Браузер нужен для настоящего рендера и отсутствующих функций. Следовать актуальным проектным ограничениям: использовать доступный браузерный плагин/встроенный браузер; не переходить к нативному управлению окнами Edge/Tilda. HTML-разбор не заменяет осмотр.

## До изменения

Сохранить только нужные исходные блоки/настройки в рабочую папку. Зафиксировать ожидаемый эффект, URL и разрешённый статус (черновик/публичная правка/публикация). Использовать точную общую форму главной и существующие интеграции. Не переподключать все формы проекта ради одной страницы.

Различать изменение страницы и проекта: шрифты, CSS/head, redirects и robots проекта затрагивают больше URL. Не делать такие правки попутно, если для локальной проблемы достаточно страницы. Не удалять намеренный noindex юридических/служебных страниц ради абстрактного «SEO score».

## Готовность и реальный рендер

Перед передачей публичной страницы или публикацией проверить фактический рендер на телефоне, планшете и широком экране. Выбрать осмысленные размеры, например 390, 768 и 1440 CSS px; это размеры проверки, не обязательные точки адаптива. Сохранить скриншоты/наблюдения с датой и URL.

Проверить:
- нет обрезанного заголовка/текста, горизонтального переполнения и случайных пустот;
- обложка тематическая, текст живой, один H1, нужные шрифты и читаемый контраст;
- изображения загрузились; alt содержателен, подписей и служебных пояснений нет;
- основные внутренние ссылки, телефон/мессенджеры ведут по нужному адресу;
- закрывающий CTA видим, доступен с клавиатуры/касанием, форма не перекрыта;
- поля формы имеют названия и понятные ошибки, клавиатура телефона подходит типу поля;
- SEO-поля, canonical, robots, schema и публичный URL соответствуют задаче.

Для черновика нужен реальный preview; если его нет — не публиковать только ради проверки без разрешения. При недоступности визуального инструмента назвать конкретный невыполненный пункт и продолжить независимую работу; не ставить отметку «визуально проверено».

## Публикация и индексация

Повторить проверку смысловых дублей и действующего разрешения. Опубликовать через MCP, затем проверить публичный URL и адаптивность; исправить обнаруженную регрессию в рамках полномочия. Завершить журнал: что изменено, какой URL, как проверено, какие ограничения остались.

Для LEDO.М действует предварительное разрешение владельца от 03.11.2026: после разрешённой публикации или существенного обновления публичного URL отправить запрос индексирования Google Search Console без повторного согласования. Перепроверить актуальное `AGENTS.md` и журнал принятых запросов, соблюдать квоты. Использовать доступную функцию «Запросить индексирование»; не подменять её URL Inspection API или неподходящим Google Indexing API. Если функции нет в MCP, назвать её отсутствие и использовать разрешённый браузер при доступе. Проверить принятие; не повторять принятый запрос без основания. Принятие не доказывает индексирование.

Яндекс-переобход/IndexNow выполнять только в пределах актуальных полномочий и реальной поддержки; не считать разрешение для GSC автоматически разрешением любых записей в других сервисах. Не создавать ключи/файлы или изменять настройки безопасности без необходимости и разрешённого объёма.
