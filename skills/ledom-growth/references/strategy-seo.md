# Стратегия, спрос и SEO

## Выбрать действие по коммерческому узкому месту

Вначале уточнить из доступных данных: какая услуга и страница продвигается, в каком регионе, откуда приходят подходящие обращения и где теряются. Не начинать автоматически с новых статей или покупки ссылок.

| Наблюдение | Следующее исследование/действие |
|---|---|
| Страница недоступна, закрыта по ошибке, canonical указывает иначе | Исправить конкретную техническую причину; сохранить намеренные исключения |
| Показы по целевым запросам есть, кликов мало | Проверить фактическую выдачу, соответствие предложения и сниппета; учитывать позицию и состав выдачи |
| Трафик есть, подтверждённых обращений мало | Проверить доставку форм, источники, соответствие аудитории/страницы и путь к обращению |
| Обращения есть, подходящих мало | Проверить квалификацию, обещания, состав услуги и соответствие сегменту |
| Подходящие обращения не доходят до договора | Проверить обработку, ожидания и причины потерь; не объявлять SEO причиной без данных |
| Предполагается нехватка внешних упоминаний | Сопоставить конкретные целевые страницы и источники конкурентов; без данных назвать гипотезой |

## Семантика и конкуренты

1. Собрать реальные запросы из доступных Вебмастера, GSC, Wordstat, Метрики и выдачи. Фиксировать поисковик, регион/устройство, период и источник. Частотность не выдумывать. Проверять, какие операторы/API и региональные настройки доступны сейчас; не использовать внутренний cookie API вместо поддерживаемого доступа.
2. Группировать по поисковой задаче: выбор подрядчика/услуги, оценка состава и стоимости, проверка процесса, реальные кейсы, ответы на технические вопросы. «Дешёвый», «премиальный» и «дизайн-проект» не считать одним намерением.
3. Для каждого кластера определить тип страницы по реальной выдаче: услуга, статья, кейс, подборка, инструмент. Читать страницы, а не только сниппеты; не оценивать длину текста по сниппету. Результаты федеральных агрегаторов не равны списку коммерческих конкурентов LEDO.М.
4. Сопоставить кластер существующему URL. Дополнить/объединить материал, если намерение уже закрыто. Новые геостраницы делать только при отдельном полезном содержании и подтверждённой работе в регионе; не размножать заменой названия города/ЖК.

Карта: кластер → намерение → текущий URL → тип выдачи → подтверждённый спрос → пробел → действие. Если выдача без подтверждённой геолокации, отметить ограничение; не называть её точным московским SERP.

## Технический аудит без механического скоринга

Разделять доступность для обхода, разрешение индексирования, выбранный canonical, наличие в индексе и способность робота увидеть содержимое. Проверять HTTP/редиректы, robots/noindex/X-Robots-Tag, sitemap, дубли, важные ссылки, mobile/content parity. Наличие URL в sitemap не доказывает индексирование; отсутствие `site:` не доказывает его отсутствие.

Сопоставлять исходный HTML и настоящий рендер там, где содержимое/ссылки зависят от JavaScript. Только HTML-проверка не подтверждает визуальное качество. Не навязывать Tilda серверные заголовки или смену фреймворка без доступного механизма и необходимости.

Разметка отражает видимое подтверждённое содержание: Organization/LocalBusiness, Service, Article, BreadcrumbList — только где уместно. Выбор типа и поддержку спецрезультатов перепроверить по официальным справкам. Не обещать звёзды/FAQ в выдаче и не добавлять выдуманный рейтинг. Не дублировать уже генерируемую Tilda разметку.

## Приоритеты и контроль изменений

Оценивать наблюдаемую проблему, охват значимых страниц/аудитории, близость к обращению, качество доказательств, стоимость и обратимость исправления. Точность формулы «SEO score» не доказывает экономический эффект. Для спорной гипотезы назвать измеряемое ожидание и условие отказа.

Перед изменениями сохранить нужные параметры/блоки и базовый замер; после — сравнить именно затронутые поля, публичную страницу и результаты. Не менять одновременно все факторы и не запускать новый полный аудит, если достаточно проверить исправление.

Основные официальные навигаторы (актуальность проверять при применении):
- https://yandex.ru/support/webmaster/ru/recommendations/intro
- https://developers.google.com/search/docs
- https://help-ru.tilda.cc/seo

При необходимости AI-видимости отдельно измерять конкретные запросы, дату, движок и источники ответа. Хорошая структура текста — гипотеза полезности, а не подтверждённая цитируемость; наличие `llms.txt` не является доказательством роста.
